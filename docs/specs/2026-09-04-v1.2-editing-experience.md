## 一、列表编辑体验（结论：无需修复，已回退）

### 1.1 有序列表「删除中间一行后编号不连续」→ 撤回

**调查过程**：

* jsdom 复现发现：模拟 keymap 链触发行首 Backspace 时，epytor `listLiftPlugin` 的 `liftListItem` 会让 ProseMirror 分裂列表（实测标签 `1. 2. 1.`），上游 `syncListOrderPlugin` 本身工作正常（程序化删除后编号正确重排）。
* 曾据此开发修复（空项放行默认删除 + lift 后接回分裂列表，含回归测试）。
* **用户实测结论（2026-09-04）**：官方三种列表（有序/无序/任务列表）在真实编辑器中体验正常，**不需要自定义处理**。分析差异：jsdom 测试模拟的是 keymap 链路径，真实浏览器中删除走 prosemirror-view 的 beforeinput 管道，实际未构成体验问题。

**决定**：撤回全部列表修复改动（已 `git checkout` 还原），不引入自定义列表插件。上游限制表（#2413/#2414/#2415）继续按原规则跟踪。

### 1.2 上游列表限制跟踪（不在本批修复）

## 二、遗留问题修复（贡献者已实现，本批 review 合并）

### 2.1 Issue #16 大文档输入卡顿（bug）——贡献分支 review 结论：**建议采纳**

* 根因已实证：`webview/editor.ts` `applyMinimalChanges` 每次保存对全文执行 O(n×m) LCS（旧版），阻塞 WebView 主线程。

* 贡献者 fork：`Jurhoo/epytor` 分支 `codex/fix-large-markdown-lag`（净改动 1 个 commit 9bf703d，+266/-104）。

* **实现质量 review**：

  * ✅ 提取独立模块 `webview/utils/minimalDiff.ts`（194 行），归一化函数完整搬移，行为与原版一致
  * ✅ 算法：唯一锚点分段 + 分段有界 LCS（`MAX_LCS_CELLS = 40_000`），无法安全匹配时**快速降级**为全量新输出（诚实退化）
  * ✅ IME 优化落实：composition 期间只暂存 pendingMd 不计算；compositionend 后一次性计算
  * ✅ 计算时机：从「每次 markdownUpdated」移到「防抖提交前」，降低频率
  * ✅ 测试 6 例：单行编辑/插入/重复行/表格风格保留/退化降级/1 万行性能断言（<1s）

* 合并前动作：rebase 到当前 dev（分支基于 main 的 9bcd0fe）；verify + 手测（大文档 + 中文 IME）。

### 2.2 Issue #15 Clean Markdown 序列化（feature）——贡献分支 review 结论：**建议采纳，但有两个决策点**

* 贡献者 fork：`codex/clean-markdown`（净改动 4 commits，+694/-4，14 文件）。

* **实现质量 review**：

  * ✅ 正路集成：官方 `remarkStringifyOptionsCtx` 扩展点 hook text handler，不 fork serializer
  * ✅ `compatible` 模式完整保留旧行为；clean 失败时 try/catch 回退 compatible
  * ✅ 配置链路完整（package.json → Provider → `window.__i18n` → 热更新消息）；`global.d.ts`/i18n 类型已同步
  * ✅ 表格 `<br />` 清理做了 fence 感知与转义管道处理；`preserveTableBreakStyle` 保留源文件拼写风格
  * ✅ spec（241 行）+ 测试（136 行）+ 双语文档齐全

* **决策点 1（产品）**：配置默认值为 `clean`——会改变所有存量用户的保存行为。建议默认 `compatible`（opt-in），或由用户拍板默认值。

* **决策点 2（正确性验证）**：`cleanTextHandler` 覆盖 `encode: []` 禁用了上游字符引用编码，`&`/`<`/`>` 等字符的输出行为变化未被贡献者测试覆盖；合并前需补测验证。

* 合并前动作：rebase 到 dev；补编码场景测试；verify + 手测。
